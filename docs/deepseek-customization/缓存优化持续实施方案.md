# DeepSeek 缓存优化持续实施方案

本文用于归档 DeepSeek 缓存优化的完整上下文，方便后续交给 Codex CLI `/goal` 持续实施。

## 背景

当前 `opencode` 二开的降 token / 降成本目标，主要依赖 DeepSeek prompt cache 的真实命中收益，而不是引入复杂 memory system。

参考方案：

- `/Users/apple/go-project/ai/DeepSeek-Reasonix/docs/CACHING.md`
- Reasonix 有 13 层缓存相关策略：DeepSeek 前缀缓存、ImmutablePrefix、追加写日志、上下文折叠、恢复修复管道、风暴抑制器、工具调用回收、截断修复、MCP 漂移检测、语义索引缓存、内存分层、延迟跟踪、事件密文编辑。

当前 `opencode` 的策略刻意保持更窄：

- 接入 DeepSeek prompt cache telemetry。
- 将 title generation、compaction 等 hidden/background 任务尽量交给 `small_model`。
- 保持 prompt / instruction 前缀顺序稳定。
- 对被截断的工具输出做确定性摘要，尤其保留失败命令的关键错误信息。
- 在真实任务数据证明必要之前，不引入 vector DB、复杂 memory layering、复杂 GC 或 LLM 写入型 memory。

## 指导原则

1. 保持 foreground 质量。
   不为了省成本而降级用户主任务模型。

2. 先观测，再扩展。
   每个优化都要能报告 cache hit tokens、cache miss tokens、total tokens、cost 和质量副作用。

3. 优先使用确定性本地转换。
   error summary、truncation repair、redaction、drift check 不应依赖 LLM 调用。

4. 保护前缀稳定性。
   system prompt、instruction 顺序、tool schema 顺序和稳定上下文块，都是 DeepSeek prompt cache 敏感的字节前缀。

5. 避免 memory 污染。
   在窄策略有真实生产数据之前，不添加 vector DB、LLM-authored memory 或 broad memory layering。

6. 小步、可回滚。
   每次只实现一层或一个窄点，配套目标测试和清晰回滚边界。

## 实施路线

### P0：可重复观测与回归护栏

目标：不是从零证明是否已经记录 cache telemetry；当前二开已经把 DeepSeek prompt cache hit/miss、cache read/write 和命中率落入 usage / session 统计。P0 的目标是把这些已有数据库记录变成可重复的真实运行证据、before/after 报告和前缀稳定性回归护栏。

任务：

- 基于当前已落库的 usage / session token 数据，增加一个类似 Reasonix `probe-loop-cache` 的 probe 或报告入口。
- 在同一个 session 中运行两轮或多轮稳定前缀请求，随后从数据库或现有统计链路读取结果。
- 汇总并输出：
  - `prompt_cache_hit_tokens`
  - `prompt_cache_miss_tokens`
  - `tokens.cache.read`
  - `tokens.cache.hit`
  - `tokens.cache.miss`
  - `tokens.cache.ratio`
  - total input/output/reasoning/cache tokens
  - total cost
- 增加 before/after 对比报告格式，便于后续评估改动是否破坏 cache hit ratio。

验收：

- 同 session 的重复前缀调用能从现有 DB / stats 链路读出明确 cache hit ratio。
- 报告能识别前缀稳定性回退，而不是只证明字段存在。
- 不改变 foreground 行为。

当前进展（2026-05-18）：

- `opencode stats --cache` 已增加 DB-backed cache report。
- 报告输出 `Prompt Cache Hit`、`Prompt Cache Miss`、`Hit Ratio`、`Cache Read`、`Cache Write`、`Non-cached Input`、`Total Accounted` 和 `Cost`。
- `opencode stats --models` 的 model 明细已补充 `Cache Hit` / `Cache Miss`，便于定位是 foreground 还是 background model 贡献了缓存命中。
- 目标测试：`packages/opencode/test/cli/stats.test.ts` 覆盖 hit/miss ratio 和无 hit/miss 时的零比率行为。
- 当前真实 DB 样本命令：

```bash
cd /Users/apple/go-project/ai/opencode/packages/opencode
PATH="$HOME/.bun/bin:$PATH" bun run --conditions=browser ./src/index.ts stats --days 1 --cache --models 3
```

示例输出摘要：37 sessions、Prompt Cache Hit 约 1.5M、Prompt Cache Miss 约 92.2K、Hit Ratio 94.3%、Cache Read 约 2.9M、Total Accounted 约 3.3M、Cost $1.0529。

### P1：前缀稳定性

目标：让 cache 敏感前缀可确定、可测试。

任务：

- 为 `Instruction.system()` 顺序增加测试：
  - global instruction 在 project instruction 之前
  - project instruction 优先级保持语义顺序，而不是字母序
  - 相同文件集合下，配置的 instruction pattern 输出稳定
- 考虑增加仅用于 debug / 测试的 prefix fingerprint：
  - system prompt blocks
  - instruction file paths
  - tool names and schema order
- 增加回归测试：相同输入下重复构造 prompt 前缀，序列化结果必须一致。

验收：

- 前缀顺序有测试覆盖。
- 未来任何 reorder 都必须是显式、可审查的改动。

当前进展（2026-05-18）：

- `packages/opencode/test/session/instruction.test.ts` 已补前缀稳定性回归测试。
- 覆盖 global instruction 必须在 project instruction 之前，即使 project 路径按字母序会排在 global 前面。
- 覆盖配置的额外 instruction 路径在重复 `Instruction.system()` 构造时输出稳定，并保持配置顺序而不是字母序。
- 不修改 runtime 行为，只锁定当前 cache-sensitive prefix 语义。

### P2：后台模型成本控制

目标：确保安全的 hidden/background work 使用 `small_model`。

任务：

- 增加 compaction 测试，证明：
  - 配置了 compaction agent model 时优先使用该模型
  - 否则使用配置的 `small_model`
  - 否则回退 foreground model
- 保持 foreground prompt 使用用户选择的主模型。
- 在 debug / test 输出中尽量报告后台任务使用的模型。

验收：

- title 和 compaction 都有 `small_model` 行为测试。
- primary agent 质量不降级。

当前进展（2026-05-18）：

- `packages/opencode/test/session/compaction.test.ts` 已补 compaction 模型选择回归测试。
- 覆盖优先级：compaction agent 显式模型 > provider `getSmallModel()` > foreground model。
- 该测试只锁定后台 compaction 模型选择，不改变 foreground prompt 的主模型。
- Full compaction test 文件已跑通：53 pass。

### P3：上下文与工具输出压缩

目标：减少低价值工具输出，同时保留调试所需信息。

任务：

- 只在存在失败或诊断信息时扩展确定性工具输出摘要。
- 工具输出被截断时，完整输出仍保存到磁盘。
- 增加测试：
  - failed tests 提取
  - file refs 提取
  - important error/warning lines 提取
  - 成功命令输出不会注入失败摘要
- 对照 Reasonix 的 context folding 思路审查现有 compaction 行为，但不要盲目照搬 50/70/80 阈值。

验收：

- 长失败 shell 输出仍保留可行动的失败原因。
- 截断后的上下文 payload 更小。
- 不因诊断信息缺失导致 `NEEDS_CONTEXT` 上升。

当前进展（2026-05-18）：

- `packages/opencode/test/tool/shell.test.ts` 已补 shell 截断集成回归测试。
- 覆盖失败且截断时注入 `<error_summary>`，并保留 key lines / file refs。
- 覆盖成功但截断时不注入失败摘要，避免污染正常输出上下文。
- `packages/opencode/test/tool/summarize.test.ts` 继续覆盖 failed tests、file refs、important error/warning lines、成功命令无摘要。

### P4：循环浪费抑制

目标：避免重复工具调用浪费 token 和 API 往返。

Reasonix 参考层：

- 第 6 层：风暴抑制器
- 第 8 层：截断 JSON 修复
- 第 12 层：延迟跟踪

任务：

- 评估一个小型 storm breaker，用于抑制重复的 `(toolName, args)` 调用。
- 不阻断正常的 read-after-edit 验证流程。
- 只对明确被截断的 tool-call args 考虑本地 JSON 修复。
- 如果真实运行中观察到慢工具或慢 MCP 重复调用，再增加低风险 latency tracking。

验收：

- 重复相同工具调用的循环减少。
- 正常 edit/read/test 工作流不受影响。
- 任何 suppression 都能在日志或事件中看到。

当前进展（2026-05-18）：

- 已将现有 `doom_loop` 三连相同 tool-call 判定抽成 `shouldAskDoomLoop`，便于锁定 storm breaker 边界。
- 已补单测覆盖：三次相同完成态调用会触发询问；read-after-edit 验证链路不触发；pending 调用不触发。
- 本阶段仅锁定既有行为，没有新增慢工具 latency tracking 或本地 JSON 修复。

### P5：MCP 漂移与密文编辑

目标：保护 cache 前缀稳定性，避免动态密钥污染可复用上下文。

Reasonix 参考层：

- 第 9 层：MCP 工具列表漂移检测
- 第 13 层：事件密文编辑

任务：

- 为 MCP tool list 增加可选 fingerprint，识别 identity 和 append-only 变化。
- 对会破坏 tool prefix 的 edit/reorder/remove 漂移进行 warning 或 reject。
- 确保 secret-like 字段在进入稳定日志或可复用上下文前被 redacted。

验收：

- 可检测 tool list drift。
- secret 不会被序列化进可复用上下文或前缀类日志。

## 暂缓项 / 非目标

以下内容在 1-2 周真实任务数据证明窄策略不足之前，不实施：

- Vector DB 或 semantic index cache。
- Broad memory layering。
- LLM-authored persistent memory。
- 自动 memory GC。
- 大规模跨语言 fixture 扩展。
- 自动启用/关闭 memory 功能。
- 完整 Reasonix recovery pipeline，除非 DeepSeek API 失败数据证明需要。
- 从 reasoning/DSML 中回收 tool calls，除非真实 DeepSeek trace 显示存在遗漏工具调用。

## 需要跟踪的指标

主要成本指标：

- total tokens per task
- input tokens
- output tokens
- reasoning tokens
- cache read tokens
- cache write tokens
- `tokens.cache.hit`
- `tokens.cache.miss`
- `tokens.cache.ratio`
- total cost

质量与回归指标：

- `NEEDS_CONTEXT` count
- verification failures
- high-risk reviewer findings
- user-visible task retries
- failed tool-call loops
- compaction frequency
- foreground model usage unchanged

目标：

- 降低 total cost 和 non-cached input tokens。
- 维持或提高 cache hit ratio。
- 不增加 `NEEDS_CONTEXT`、verification failure rate 或 serious review findings。
